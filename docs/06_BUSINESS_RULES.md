# Business Rules

UI presentation is intentionally excluded.

## Roles and permissions

- Every valid account has buyer access.
- Seller includes buyer access.
- Admin includes seller and buyer access.
- Legacy `role: admin|seller` is normalized for compatibility.
- Default view priority: Admin → Seller → Buyer.
- Only an approved/valid non-admin seller may own an Admin-created project.
- Blocked seller status aliases include pending, rejected, suspended, disabled, inactive, revoked, and (backend) deleted.
- Users may not change their own permission map.

## Property ownership and lifecycle

Canonical statuses:

```text
draft -> pending -> approved -> active -> inactive/sold
                    \-> rejected (from pending review)
```

- Seller-created projects are owned by the authenticated seller and start `pending`.
- Admin-created projects must be assigned to a currently valid seller and start `pending`.
- Seller-submitted changes return the project to `pending`.
- Admin review approves or rejects; approval does not itself make the property buyer-visible.
- Admin activates an approved property separately.
- Protected status/review fields are removed from untrusted change payloads.
- Publishing requires: valid seller, name ≥ 2 characters, cover/hero image, valid non-zero coordinates, and positive starting price.
- Ownership changes require the Admin assignment workflow.
- Property lifecycle changes create audit records.

## Buyer visibility

- A project is buyer-visible only when `project.status === "active"`.
- No approval alias, legacy spelling, boolean, or display configuration overrides this rule.
- Owners and Admin can read non-active projects as authorized.
- Buyer surfaces must use `isPublicProperty`/`isProjectPublishable`.

## Search and filters

- Project text search matches stored project name, village, taluka, or developer, case-insensitively.
- Search results are derived only from active projects already allowed by current filters.
- Home search returns at most eight project matches.
- Location suggestions may come from Google Places; they are not Zinoo inventory.
- Current filters: maximum budget, selected land zones, selected NA statuses, bank-loan availability, and utility-supported minimum score where used.
- Filters do not fabricate missing values.

## Map and layouts

- Only projects with valid coordinates can be represented spatially.
- Coordinate compatibility order: top-level latitude/longitude, nested location, then legacy coords.
- `(0,0)` is invalid.
- Layout records belong to a project through `projectId`.
- Admin or project owner may create/update/delete layouts; authorized viewers may read layouts for active projects.
- Geometry-derived values must use existing geometry utilities, not manual approximations.

## Leads and visits

- A visit is created by the authenticated buyer and linked to the selected project and project owner.
- Visit submission requires buyer name, phone, and date in current UI.
- When booking a visit, the client creates a lead if no loaded lead has the same phone.
- Creator and assigned project owner may read activity; Admin has oversight.

## Cashback

- A buyer submits against an existing eligible project with required purchase inputs and proof.
- The backend reads the project and computes the amount; client-provided totals are not trusted.
- Formula: `cashbackAmount = purchasedAreaSqFt × (project.cashbackPerGuntha ?? project.cashbackAmount)`.
- Rate and area must produce a valid positive amount.
- Initial status: `Pending Seller Approval`.
- Assigned seller may approve to `Pending Admin Approval` or reject with a reason.
- Admin may approve `Pending Admin Approval` to `Payment Pending`, or reject with a reason.
- Admin may mark `Approved` or `Payment Pending` claims paid only with payment date (`YYYY-MM-DD`), method, and transaction reference.
- Every transition is transactional, audited, and creates a buyer notification.
- Claims cannot be created, updated, or deleted directly by clients.

## Feed banners

- Admin only manages banners.
- Maximum five display-order positions, integers 1–5.
- Feed document keys are exact; extra fields are rejected.
- Image must be JPG, PNG, or WebP and ≤10 MB.
- Storage path is generated by the function and cannot be chosen arbitrarily.
- Signed-in users see active banners; Admin can see all.

## Documents and verification

- Project media/documents are readable only to authenticated users under current Storage rules.
- Buyer project details show documents only when enabled, configured for details, and verified.
- Upload type/size restrictions in Storage rules are authoritative.
- Verification is stored state; UI may not infer it from filename/type.

## Notifications

- Only trusted backend code creates/deletes notifications.
- A recipient may only change `read` and `readAt`.
- Notifications are scoped by `recipientId`; Admin can read all under rules.

## Restrictions and TODOs

- No payment gateway or automated fund transfer is implemented.
- Favorites have no persistence/business contract.
- No property deletion/cascade policy is defined.
- No commission-vs-cashback distinction beyond existing stored aliases is approved.
